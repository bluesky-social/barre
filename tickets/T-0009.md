This is a deliberate fix of a Yoga bug (yoga#1932, conformance/divergences.md and the target
test file's own comment, which has the full repro tree and confirmed root cause), not a port.

Root cause, confirmed by reading the code (not guessed): when a node's own width and height are
both already definite, and the current pass is measure-only (`!perform_layout`), barre's
`calculate_layout_internal` takes the `measure_node_with_fixed_size` fast path
(`calculate_layout.rs`, the `if !perform_layout && measure_node_with_fixed_size(...)` branch):
it sets the node's own measured dimensions directly from its style and returns, *without*
recursing into the node's children at all. This is a real, intentional Yoga optimization
("if we're not being asked to perform a full layout we can skip the algorithm if we already
know the size") and is correct on its own — it must not be removed or weakened for the general
case.

The bug is that `calculate_baseline` (`baseline.rs`) can be asked for the baseline of exactly
such a short-circuited node. `calculate_layout_impl` calls `calculate_baseline(child)` for a
baseline-aligned child in three places (grep `calculate_baseline` in `calculate_layout.rs`):
once while computing a flex line's cross size, and twice more while positioning children along
the cross axis. If `child`'s own layout came from the fixed-size fast path, its children were
never recursed into, so when `calculate_baseline` falls through to a *grandchild* with no
baseline function and no children of its own, that grandchild's `measured_dimension(Height)`
was never written and is NaN (or whatever `LayoutResults::reset` leaves it as) — the target
test's tree is exactly this: a 200-wide `alignItems: baseline` row (sized by its content, so it
is measured before it is finally laid out) holding one 100x100 item which itself holds one
childless item.

Fix it where the baseline is actually needed, not by weakening the fixed-size fast path: before
`calculate_layout_impl` reads a baseline-aligned child's baseline (at each of the three call
sites), make sure that child's subtree has real (not NaN) measured dimensions down to whatever
depth `calculate_baseline` will actually read — e.g. by giving that specific child a real
recursive layout pass instead of letting it take the fixed-size shortcut, when it is about to be
used as a baseline reference. Check your fix against all four failing tests in the target file,
and against the fifth (`baseline_row_item_without_children`, already passing) to make sure it
stays passing — that one has no unmeasured grandchild, so your fix must not change its layout.

- Don't change `is_baseline_layout` or `resolve_child_alignment`; this is only about making sure
  baseline data exists before it is read, not about who gets aligned to what.
- Every changed function's doc comment says where and why it deliberately differs from Yoga,
  citing yoga#1932.
- Run the full `./conf` suite, not just the target: this touches a path every flex container
  with `alignItems: baseline` goes through, so check for regressions beyond the target file.
