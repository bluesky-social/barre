A deliberate fix of a Yoga bug, not a port. barre must lay a tree out the same way whether it is
laid out fresh or relaid out after earlier layouts at other sizes (`conformance/divergences.md`,
yoga#1552 and yoga#2019). Everything in `conformance/expected-pass.txt` must stay green, including
the measure-callback counts in `YGMeasureCacheTest`/`YGMeasureModeTest` and the `hasNewLayout`
checks in `YGContentsNodeHasNewLayoutTest`.

This ticket has failed four times because its earlier text was ambiguous. Below is one exact
design. An architect-side prototype of exactly this design, on current main, passes the whole
target with no regressions in the full suite. If yours doesn't, you have deviated from it. Do not
redesign it, and do not substitute any of the shortcuts listed under "Do not".

## How Yoga's flex basis depends on history

`computeFlexBasisForChild(node = P, child = C, ...)` is only ever called from P's
`calculateLayoutImpl` (through `computeFlexBasisForChildren`), with P's inner available sizes as
both `width`/`height` and `ownerWidth`/`ownerHeight`. It takes the **resolved branch**
(`useResolvedFlexBasis`) exactly when C's processed flex basis is not `auto`
(`Node::processFlexBasis`: an explicit `flexBasis`, or `flex > 0` without web defaults, which
gives a basis of 0) **and** P's inner main size is defined (P's main-axis sizing mode is not
`MaxContent`). In that branch Yoga writes the resolved value only if C's stored
`computedFlexBasis` is undefined. Otherwise it keeps what is stored. Every other branch always
overwrites (definite width/height, or measuring C's content with `calculateLayoutInternal(C, ...,
performLayout = false)`), and so does the `singleFlexChild` shortcut in `computeFlexBasisForChildren`.

Within one layout this retention is intended and the suite depends on it. A max-content pass over
P (main axis `MaxContent`) stores each child's content size. A later definite pass over P keeps
it. That is why a `flex: 1` text under a scroll view gets its content height. So within one
generation, C's basis is "the last value written by a run of P in this layout, or the resolved
value if no run of P in this layout has written it yet". A fresh tree starts with every basis
undefined.

Across layouts, Yoga goes wrong in two ways, and both must be fixed.

1. **yoga#1552.** No run of P in this layout has written C's basis yet, but a value from an earlier
   layout is stored. Yoga keeps it, for example a percent basis resolved against the old size.
   A fresh layout would write **the resolved value** here. Measuring the content would be wrong
   too: an empty `flexBasis: 25%` child would collapse.
2. **yoga#2019.** Earlier in this layout, a call to P was answered from a cache entry stored in an
   **earlier** layout, so P's run was skipped. In a fresh layout that call would have run and
   rewritten C's basis, typically with a content size from a max-content pass. The later definite
   run of P then reads whatever an earlier layout left. A fresh layout would read **what the
   skipped run wrote**, which is not the resolved value. Concrete shape: two `flex: 1` texts of
   different lengths in one auto-height wrapper under a scroll view, laid out at portrait, then
   landscape, then portrait. If the stale basis is replaced by the resolved value (0), the two
   texts split the wrapper's height equally. A fresh layout gives each its own content height.
   Writing the resolved value is therefore wrong in this case, even though the target tests may
   not catch it.

Plus a third, cache-side case: (3) a call to P answered from an earlier layout's cache entry,
whose run read retained child bases that were written under different conditions than the ones
this layout has established for P.

## The design: per-node flex-basis anchor

**Anchor.** For a node P with layout children and no measure function, in generation G, the
anchor is the most recent call `calculate_layout_internal(P, ...)` in G after which, in a fresh
layout, P's children hold freshly rewritten bases. A call **starts a new anchor** when either of
these holds:

- it is P's first call in G (`layout.generation_count != generation_count` on entry; Yoga sets
  `generationCount` at the end of every visit, so read it before that store);
- P's main-axis sizing mode is `MaxContent` (main axis from `is_row(node.style().flex_direction())`:
  width mode if row, else height mode). Such a run sends every non-`auto`-basis child through a
  rewriting branch.

All other calls in G either read retained bases (keep) or hit a same-generation cache entry. A
same-generation hit also happens in a fresh layout, so it rewrites nothing and never moves the
anchor.

Implement these changes. D1 to D5 are the deliberate differences from Yoga that this ticket asks
for. Each one's doc or inline comment must say so, citing yoga#1552 and/or yoga#2019.

**D1. `compute_flex_basis_for_child`, resolved branch.** Drop the `WebFlexBasis` gate. The
condition becomes `is_undefined(stored basis) || computed_flex_basis_generation != generation_count`.
The body stays as Yoga's: `max_or_defined(resolved, padding_and_border)`, then the stamp at the end
of the function. This is the whole change in this function. With D3 and D4 in place, a stale
stamp here means no run of P in this layout (real or skipped) has written C's basis. That is
exactly the state in which a fresh layout writes the resolved value, so this write is correct and
is not a stand-in. Say this in the comment. The `WebFlexBasis` feature becomes the default
behaviour. The suite's `WebFlexBasis` test (`YGRelayoutTest.dont_cache_computed_flex_basis_between_layouts`)
stays green.

**D2. `layout_results.rs`.**
- `CachedMeasurement` gains `generation: u32`, the generation of the run that stored the entry,
  and the anchor key in effect for that run: `anchor_available_width: f32`,
  `anchor_available_height: f32`, `anchor_width_sizing_mode: SizingMode`,
  `anchor_height_sizing_mode: SizingMode`. Defaults: generation 0, NaN, NaN, `MaxContent`,
  `MaxContent`. Order the fields so `repr(C)` adds no avoidable padding.
- A new `#[repr(C)] #[derive(Copy, Clone, Debug)] pub struct FlexBasisAnchor` holds `generation:
  u32`, `available_width`, `available_height`, `owner_width`, `owner_height: f32`,
  `width_sizing_mode`, `height_sizing_mode: SizingMode`, `owner_direction: Direction`, `reason:
  LayoutPassReason`, and `replay_pending: bool`. These are everything needed to re-issue the call
  to `calculate_layout_impl`. The `Default` has generation 0 (never current; the counter starts at
  1, the same assumption Yoga makes for `generationCount`) and `replay_pending: false`.
- `LayoutResults` gains `pub flex_basis_anchor: Cell<FlexBasisAnchor>`. Add it to `Default`, and
  to `copy_from` explicitly, because `copy_from` lists fields by hand and `reset` uses it.
- Everything stays `Copy`, fixed-size and pointer-free, and the `needs_drop` assert stays. In the
  doc comments, give the size each struct and `LayoutResults` gain, computed with `size_of` rather
  than guessed, and why each field is needed. T-0010 (owner sizes in the cache key, yoga#1626/#1003/#1784)
  will extend these same structs, so keep them easy to extend.

**D3. `calculate_layout_internal`: track the anchor, and replay a skipped anchor before a real run.**
Keep Yoga's code exactly as it is for measure-function nodes, nodes without layout children, and
same-generation hits. Do not change `find_cached_result` or `can_use_cached_measurement`
(`cache.rs` is out of scope): the lookup is Yoga's, and D5 only post-filters its answer. After
`need_to_visit_node` and the existing `find_cached_result` call:

```
let has_children = !node.has_measure_func() && node.layout_child_count() > 0;
let stored = layout.flex_basis_anchor.get();
let starts_anchor = layout.generation_count.get() != generation_count
    || main_axis_sizing_mode == SizingMode::MaxContent
    || stored.generation != generation_count;      // defensive: no anchor yet this layout
let this_call = FlexBasisAnchor { generation: generation_count, available_width, available_height,
    owner_width, owner_height, width_sizing_mode, height_sizing_mode, owner_direction, reason,
    replay_pending: false };
let anchor = if starts_anchor { this_call } else { stored };
// D5 runs here; it may turn a hit into a miss.
```

- **Hit path** (`!need_to_visit_node` and a hit survives D5): Yoga's code, plus one addition. If
  `has_children && starts_anchor && entry.generation != generation_count`, set
  `flex_basis_anchor = FlexBasisAnchor { replay_pending: true, ..this_call }`. In a fresh layout
  this call would have run and rewritten the children's bases. Here it was answered from an
  earlier layout, so record it for replay.
- **Run path** (everything else): if `has_children`, then
  1. `let pending = layout.flex_basis_anchor.get();` if `pending.generation == generation_count &&
     pending.replay_pending`, first store `FlexBasisAnchor { replay_pending: false, ..pending }`,
     then call
     `calculate_layout_impl(node, pending.available_width, pending.available_height,
     pending.owner_direction, pending.width_sizing_mode, pending.height_sizing_mode,
     pending.owner_width, pending.owner_height, false /* perform_layout */, pending.reason,
     layout_marker_data, depth, generation_count)`. This re-runs, measure-only, the call that the
     cache skipped, so P's children get exactly the bases (and the calls to their own
     subtrees) that a fresh layout gave them before this call. It is `calculate_layout_impl`, not
     `_internal`: no cache lookup, no cache store, no `generation_count` or `hasNewLayout` update. The real run
     right after overwrites everything this sets on P itself (measured size, margins and so on);
  2. then, if `starts_anchor`, set `flex_basis_anchor = this_call` (`replay_pending: false`);
  3. then Yoga's `calculate_layout_impl` call and the rest of the function, unchanged except for
     the store (D4).
  The replay runs only immediately before a run that happens anyway. So it never makes Yoga skip
  less work, never clones children Yoga would not clone, and never stamps `hasNewLayout`.

**D4. `calculate_layout_internal`: stamp stored entries.** Every `CachedMeasurement` written by the
store at the end of the run path also records `generation: generation_count` and the four
`anchor_*` fields from `anchor` (the anchor in effect for this run). Yoga's store condition
(`cached_results.is_none()`), its slot choice, `next_cached_measurements_index` wrap-around and
`max_measure_cache` bookkeeping are unchanged, with one exception, D5's rejected entry.

**D5. `calculate_layout_internal`: refuse an earlier layout's entry computed under a different
anchor.** If `!need_to_visit_node`, the lookup hit an entry with `entry.generation !=
generation_count`, `has_children`, **and** P has at least one layout child whose basis can be
retained, check whether the entry's four `anchor_*` fields match `anchor`'s (`inexact_equals` for
the sizes, so NaN equals NaN; `==` for the modes). If they do not match, treat the lookup as a
miss and remember which entry was rejected. A child's basis can be retained when, iterating
`node.layout_children()`, the child has `display() != Display::None`,
`position_type() != PositionType::Absolute`, and `!child.process_flex_basis().is_auto()`. Put this
check in a small private helper in `calculate_layout.rs` that says so, and evaluate it only in this
case (an earlier-generation hit on a node with children), never on every call. When the run path
stores the result of a rejected lookup, it overwrites the rejected entry in place (the same
measurement slot, or `cached_layout`), with no new slot and no change to
`next_cached_measurements_index` or `max_measure_cache`. That keeps cache occupancy what Yoga's
would be after a hit.

Why the "retained child" condition matters: without it, D5 also refuses entries whose results
cannot depend on retained bases. That breaks
`YGContentsNodeHasNewLayoutTest.contents_child_hasNewLayout_not_stamped_on_measure_only_visit`,
where Yoga must reuse the layout cache. Why D3 has no such condition: a skipped call on a node with
only `auto`-basis children still skips the calls to its descendants that set *their* anchors (the
issue's wrapper chain). Restricting D3 the same way breaks `rotate_and_back_scrollview_one_wrapper`.

## Do not

Each of these was tried, and each failed review or the suite.

- **Do not stamp the child's basis with constraints** (container size, owner sizes, direction), or
  treat a same-generation basis as stale when P's sizes differ. A fresh layout keeps a
  same-generation basis whatever P's current sizes are. The constraints belong in P's anchor and in
  the cache entries' anchor key (D2 to D5). Direction is already covered by Yoga:
  `last_owner_direction != owner_direction` sets `need_to_visit_node`, which invalidates every
  cache entry.
- **Do not measure content unconditionally when the stamp is stale.** That breaks the yoga#1552
  case above. Content is measured only by replaying the recorded anchor call (D3), which goes
  through Yoga's own branches.
- **Do not write the resolved value in place of a skipped content pass.** This is the "stale ⇒
  resolved" shortcut without D3, the two-texts case above. With D3, D1's resolved write only
  happens when no anchor exists to replay.
- Do not refuse every earlier-layout cache entry for containers, or every one whose main axis is
  `MaxContent`. That re-lays out every scroll view's content on every commit, and Yoga keeps
  those caches on purpose (`YGFlexBasisFitContentTest.scroll_avoids_remeasure`).
- Do not touch the measure-function leaf cache path or `can_use_cached_measurement`, and do not
  add owner sizes to cache keys. Those belong to T-0010.

## Out of scope (not defects of this ticket)

Each of these makes some relayout differ from a fresh layout through a different mechanism. Do not
try to fix them here. If you see one, mention it in your summary.

- **A node's own percent padding, margin or min/max, resolved against an owner size that changed
  while what the node is offered did not** (yoga#1626, #1003, #1784). This is T-0010, which needs
  this ticket. The example "root width changes; a child with a fixed width and percent
  `paddingLeft` keeps its old padding, so its child's percent basis is resolved against the old
  inner width" is this class. The child's own padding is already wrong before any flex basis is
  involved. No flex-basis design can fix it, because every call to that child is a cache hit.
- Measure-function leaves reused across layouts through `can_use_cached_measurement`'s
  compatible-size rules, and pixel-grid rounding re-applied to subtrees whose layout came from the
  cache.
- **History more than one level deep.** D5 compares P's own anchor only. P's cached result can still
  depend on its descendants' anchors from the earlier layout. Checking that would mean walking the
  subtree on every cache hit, which is the same as having no cross-layout cache.
- **The `singleFlexChild` zero basis written by a skipped `StretchFit`-main call.** Such a call
  is not an anchor.
- **Cache-slot occupancy.** Earlier-layout entries take up slots, which can evict a same-layout
  entry earlier than in a fresh layout.
