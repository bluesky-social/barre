This is a deliberate fix of three related Yoga bugs (conformance/divergences.md), not a port.
All three are the same root cause: barre's `CachedMeasurement` (`cache.rs`, ported faithfully
from Yoga in T-0006's wider cache work) is keyed only on `available_width`, `available_height`,
`width_sizing_mode` and `height_sizing_mode` (plus the stored `computed_width`/`computed_height`
it compares against). On a relayout, a child offered the *same* available size and sizing mode
as last time can hit this cache even though something else that its layout actually depends on
has changed since:

- **yoga#1626**: a node's own percent-resolved padding and margin depend on its *owner's* width
  and height, not on the available size/mode it was offered. Resizing an ancestor changes the
  owner size without changing what this node is offered, so a cache hit keeps padding/margin
  resolved against the old owner size.
- **yoga#1003**: `can_use_cached_measurement`'s "does the new AtMost height still fit the old
  measurement" check doesn't account for the node's own min/max height, which can themselves be
  percentages of the owner's height; a cache entry valid before an owner resize can stop being
  valid after one without `can_use_cached_measurement` noticing.
- **yoga#1784**: a measure function is given `availableWidth` already adjusted for the node's own
  padding/border and (if applicable) percent-resolved margins; when the owner's width changes
  without changing what this node itself is offered (e.g. the node has a fixed width but a
  percent padding), the measure function should be called again with the new effective width,
  but a cache hit skips the call and keeps the old measurement.

Fix the cache key, not each symptom separately: find every input `can_use_cached_measurement`
and the `CachedMeasurement` struct it compares against currently omit that these three bugs show
are actually load-bearing (owner width, owner height, and anything that already resolves against
them before a measurement is taken or cached — re-derive this from Yoga's actual call sites
rather than guessing, with `./spec --refs`), and add exactly those fields, stamped at store time
and checked at lookup time, alongside what is already keyed. Keep `CachedMeasurement` (and
anything in `layout_results.rs` it touches) `Copy`, fixed-size and pointer-free (docs/API.md; the
RN shim needs it) — say in your doc comment how many bytes this adds and why each field is
needed.

- This builds on T-0006's design (the generation/constraints stamp it adds to guard stale
  flex-basis reuse): read what T-0006 actually landed as before starting, and use the same stamp
  or a compatible extension of it rather than a second, parallel mechanism, if that fits. If
  T-0006's landed design doesn't give you enough to key on (e.g. it doesn't carry owner size),
  say so in your doc comment and extend it; don't duplicate state that already exists.
- Keep Yoga's existing `CachedMeasurement`/layout-cache equality and lookup structure
  (`sizeIsExactAndMatchesOldMeasuredSize`, `oldSizeIsMaxContentAndStillFits`,
  `newSizeIsStricterAndStillValid`) for everything it already gets right; you are adding keys to
  it, not replacing it.
- After your change, run the **full** `./conf` suite, not only the three target files: a cache
  key is read everywhere the cache is, so check for regressions broadly, and specifically check
  `YGMeasureCacheTest` and `YGMeasureModeTest` (measure callback counts) do not change — making
  the cache correctly *stricter* must not make it falsely stricter where Yoga's own suite (today
  passing) depends on a cache hit happening.
- If you cannot find a cache-key fix that resolves all three without regressing something already
  in `conformance/expected-pass.txt`, reply `BLOCKED: <what regresses and why>` rather than
  forcing a partial fix through; this is exactly the kind of design tradeoff an architect should
  see, not guess around. In particular: a prior attempt at this ticket added owner width/height
  and owner-dependent padding/margin/min-max to the key (a sound shape, keep that direction), then
  found yoga#1784's own target tests still failed only for a container whose *own* resolved width
  is a percentage of a resizing ancestor (the issue's shape: fixed paddings, a percent-width
  container). That container's `available_width` genuinely differs between two panel sizes, but
  `can_use_cached_measurement`'s pixel-grid rounding tolerance (intended for ordinary float noise)
  can round both to the same value, so Yoga's own existing `available_width` comparison — which
  this ticket's key additions sit alongside, not replace — reports a hit anyway. The attempt then
  special-cased a *bypass* of that rounding tolerance (a new scale-free comparison, used only for
  measure-function nodes when the owner size had changed) to force a miss; the verifier correctly
  rejected it as invented, not Yoga-conditioned, and tuned to the target test's numbers. **Do not
  reintroduce that bypass or anything shaped like it** (changing how or when the existing rounded
  comparison applies). If the right key addition still doesn't close this specific case, reply
  `BLOCKED` naming exactly this container-percent-width-vs-rounding tension; it may be that this
  one sub-case needs the architect's judgment on whether rounding tolerance and owner-size caching
  can coexist at all, not a cleverer key.
- Every changed function's doc comment says where and why it deliberately differs from Yoga,
  citing the three issue numbers for whichever fields address them.
