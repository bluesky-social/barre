A previous attempt at this ticket was accepted and merged (it was a correct, honest, behaviour-
preserving simplification) but did not actually fix the regression: the gate's own benchmark table
still showed `rn/feed50/rotate` barely moved (around 1.4-1.5x Yoga's time, against the target
below). The verifier's questions are about honesty, not about hitting a number, so an honest change
that doesn't move the needle can still be accepted; this ticket's `check` now asserts the ratio
itself (see below), so a diff that doesn't actually speed things up fails the gate. Keep looking for
the real bottleneck; the previous attempt's small simplification is already on the branch and worth
building on, but is not the fix.

This is a performance-only ticket: no behaviour changes, every pixel of every layout must stay
exactly what it is today. `rn/feed50/rotate` (`bench/` benchmarks barre against real Yoga through
the identical C API, docs/BENCH.md) got noticeably slower when T-0006's flex-basis anchor and
replay mechanism (yoga#1552, yoga#2019) landed in `calculate_layout_internal` and
`compute_flex_basis_for_child`: the same workload, same measure-call counts, same new-layout-node
counts, but more wall-clock time. Before T-0006, `rn/feed50/rotate` (and the other `rn/feed50/*`
relayout workloads) ran at roughly 0.6-0.65x Yoga's time on this machine; it should again, not at
parity with or slower than Yoga.

Since measure calls and new-layout counts are unchanged, the extra time is pure engine overhead:
something in T-0006's anchor-tracking or replay path (`calculate_layout_internal`'s anchor
bookkeeping, the `FlexBasisAnchor` read/write on every visit, the D5 cache-entry comparison, or the
D3 replay call itself) runs, or runs more work, on a plain resize where it did not have to.

- Read T-0006's landed code closely (`git log --oneline -- crates/barre/src/algorithm/calculate_layout.rs`
  to find it) before guessing. Profile first (`bench/profile rn/feed50/rotate`, docs/BENCH.md) to
  find where the extra time actually goes, rather than optimising by inspection. A likely shape:
  work that only needs to happen when a D3 replay is pending, or only for nodes with a retainable
  flex-basis child, running unconditionally instead.
- Whatever you change must still implement T-0006's design exactly (every target test in
  `barre/YGFlexBasisRelayoutTest/` and `barre/YGStaleFlexBasisTest/` stays green, and so does
  everything else in `conformance/expected-pass.txt` — run the full `./conf` suite, not just those
  two files). This is restructuring for speed, not a new design; if speeding it up seems to require
  changing what it computes, stop and reply `BLOCKED: <what you'd have to change and why>`.
- The gate's second check command re-reads the benchmark's own JSON output and fails if the
  checksums or measure/new-layout counts differ from Yoga's, or if the barre/Yoga ratio isn't below
  0.9 (the real goal is about 0.7x; 0.9 is just the gate's floor, so don't stop at "barely passes").
  Report the actual ratio you achieved in your summary regardless.
- `bench/run --quick` also covers the other `rn/feed50/*` workloads, which touch the same code;
  check they don't regress either, even though only `rotate` gates.
- Don't touch `bench/` (another agent owns it) or anything outside `calculate_layout.rs`. The
  check's `rm -rf vendor && ln -sfn ...` is only pointing your worktree's `vendor/` (empty here;
  your tree has no submodules) at the real one so `bench/run` can build Yoga for comparison — it
  is not touching `bench/` itself, and you don't need to repeat or understand it beyond that.
