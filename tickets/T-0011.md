**Parked (tier = architect).** Five swarm attempts (1 merged-but-insufficient, 3 revise, 1 BLOCKED)
established that this doesn't fit the swarm: workers can't run `bench/run`/`bench/profile`
themselves (sandbox-denied, confirmed live), so they're reasoning blind between gate reports, and
the real fix now needs a cached per-node flag threaded through `node/mod.rs` (see below) rather
than a `calculate_layout.rs`-only change. An architect-led perf agent is taking this over in its
own worktree; the analysis below (the D3 replay's cascading cost, the scope it actually needs) is
left as a starting point, not a prompt to reopen into the swarm.

A previous attempt at this ticket was accepted and merged (it was a correct, honest, behaviour-
preserving simplification) but did not actually fix the regression: the gate's own benchmark table
still showed `rn/feed50/rotate` barely moved (around 1.4-1.5x Yoga's time, against the target
below). The verifier's questions are about honesty, not about hitting a number, so an honest change
that doesn't move the needle can still be accepted; this ticket's `check` now asserts the ratio
itself (see below), so a diff that doesn't actually speed things up fails the gate. Keep looking for
the real bottleneck; the previous attempt's small simplification is already on the branch and worth
building on, but is not the fix.

This is a performance-only ticket: no behaviour changes, every pixel of every layout must stay
exactly what it is today. `rn/feed50/rotate` (`bench/` benchmarks barre against real Yoga through
the identical C API, docs/BENCH.md) got noticeably slower when T-0006's flex-basis anchor and
replay mechanism (yoga#1552, yoga#2019) landed in `calculate_layout_internal` and
`compute_flex_basis_for_child`: the same workload, same measure-call counts, same new-layout-node
counts, but more wall-clock time. Before T-0006, `rn/feed50/rotate` (and the other `rn/feed50/*`
relayout workloads) ran at roughly 0.6-0.65x Yoga's time on this machine; it should again, not at
parity with or slower than Yoga.

Since measure calls and new-layout counts are unchanged, the extra time is pure engine overhead:
something in T-0006's anchor-tracking or replay path (`calculate_layout_internal`'s anchor
bookkeeping, the `FlexBasisAnchor` read/write on every visit, the D5 cache-entry comparison, or the
D3 replay call itself) runs, or runs more work, on a plain resize where it did not have to.

- Read T-0006's landed code closely (`git log --oneline -- crates/barre/src/algorithm/calculate_layout.rs`
  to find it) before guessing. You cannot run `bench/run` or `bench/profile` yourself (not in your
  sandbox; a prior attempt confirmed this) — reason about the hot path by reading the code, and
  rely on the gate's own check output (fed back as a note on your next attempt if this one doesn't
  land) for the actual before/after ratio instead of guessing blind.
- A prior attempt (BLOCKED, no diff) traced the cost: a container's first call in a layout answered
  from an earlier layout's cache later runs a full measure-only `calculate_layout_impl` (D3's
  replay), which hits stale entries in *its* children too, cascading the replay down the subtree.
  Skipping a replay that can't change anything (no descendant holds a retainable flex basis) needs
  to know that cheaply, not by walking the subtree on every visit (O(n·depth), probably still too
  slow). That's why `layout_results.rs` and `node/mod.rs` are now in scope: add a cached per-node
  flag (e.g. "this node or something in its subtree has a child whose flex basis can be retained"),
  computed once and kept current wherever `node/mod.rs` changes a node's style or children (style
  setters, `insert_child`/`remove_child`/`remove_child_at`, anywhere else that can change whether a
  child's basis is retainable) — the same kind of invalidation `mark_dirty_and_propagate` already
  does, so look at how that propagates and whether this flag needs the same propagation shape or a
  different one. Keep it `Copy`/fixed-size per docs/API.md, as everything else in these structs is.
  If maintaining this flag correctly turns out to need touching files outside this scope too, or a
  shape that conflicts with existing fields, say so in a `BLOCKED` reply rather than guessing.
- Whatever you change must still implement T-0006's design exactly (every target test in
