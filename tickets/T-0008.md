This is a deliberate fix of a Yoga bug (yoga#2035, conformance/divergences.md), not a port:
`calculateFlexLine` sums each item's flex basis *after* clamping it to the item's min/max
(`bound_axis_within_min_and_max`, barre's `flex_line.rs`) into `sizeConsumed`, and both
distribution passes (`distributeFreeSpaceFirstPass`/`SecondPass`,
`resolve_flexible_length` in `calculate_layout.rs`) start each item from that clamped value
too. CSS Flexbox section 9.7 computes free space and distributes it from the *unclamped* flex
base size, freezing an item at its min or max only when the distribution would otherwise push
it past that bound (and then redistributing the remainder among the rest). This isn't gated by
an errata bit: Yoga is simply wrong here, with the default config, `YGErrataNone` and
`useWebDefaults`. The target test's own file documents the concrete expected values from
Chrome/Firefox/Safari.

Port CSS 9.7's algorithm (summing unclamped flex-basis for the initial free-space calculation,
freezing items whose flex basis already violates their min/max before the main distribution
loop runs, same as frozen items are already excluded from the running totals today) into
`size_consumed`, `distribute_free_space_first_pass`, `distribute_free_space_second_pass` and
`resolve_flexible_length`. Keep the existing min/max clamping Yoga does apply correctly
elsewhere in these functions (per-item bounding during the actual distribution passes, the
`totalFlexShrinkScaledFactors`/`totalFlexGrowFactors` running totals, #2006's already-fixed
running-totals behavior and its errata bit) — this ticket is only about what the *initial* free
space and each item's *starting point* for distribution are computed from.

- This changes a foundational quantity that the whole flex algorithm's main-axis sizing reads.
  After your change, run the **full** `./conf` suite (not just the target), not only the two
  tests here: everything in `conformance/expected-pass.txt` must still pass, with no
  regressions. If you cannot find a change that fixes the target without regressing something
  already passing, stop and reply `BLOCKED: <what regresses and why>` rather than forcing it
  through — this needs an architect's judgment call, not a special case.
- Every changed function's doc comment says where and why it deliberately differs from Yoga,
  citing yoga#2035.
- Don't touch the already-correct #2006 running-totals fix or its errata gate
  (`Errata::FLEX_FIRST_PASS_USES_RUNNING_TOTALS`).
